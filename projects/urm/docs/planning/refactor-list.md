# URM core refactor list

Status: target design, disposition list for the 92 Python files that were under `src/urm/` when this plan was written, and executable instructions after the cutover ending at `b4fa6d6`. That cutover moved many files but did not establish the functional end state. A destination row is an ownership decision, not evidence that compilation, execution, or coverage works. Exact helper filenames can change when dependency direction and executable contracts justify it; the behavioral gates below cannot be waived by a file move.

## End-state rules

1. `src/urm/` contains only the public mixer frontend, typed semantic IR, compiler, plan binder/runtime, three native mixer backend families (K1/K2/K3), and independent NumPy/PyTorch reference backends. No model architecture, named coverage catalog, upstream comparator, training loop, inference engine, benchmark, test fixture, or profiling harness lives there.
2. Every compiler pass has one owner and a subdirectory: `normalize/`, `rewrite/`, `partition/`, `select/`, `placement/`, `schedule/`, `lower/`, `verify/`, `cost/`, and `solve/`. Shared diagnostics may live in `compiler/common/`. `ir/` owns semantic types and effects; backends must not import compiler internals.
3. `backends/triton/k1`, `k2`, and `k3` contain GPU kernel bodies, autograd/backward implementations, narrow launchers, and declarative capability facts. Candidate choice, rewrite, probing policy, cost, tuning, partitioning, and route/state composition belong to compiler stages. Runtime binds and invokes **the compiled plan**; it does not redispatch from the recipe name or rederive a launch schedule.
4. Every named coverage recipe is a versioned JSON document outside `src/urm/`. A recipe may declare a kernel fragment or a complete model graph, but it must state which. JSON refers only to registered typed operations, parameter transforms, state/cache contracts, and graph edges. It cannot hide Python callbacks or use an architecture name as an execution switch. Model-specific components, when a typed reusable operation is insufficient, live under `architectures/` and are explicitly outside URM core. An unrepresentable component makes the full-model row unsupported rather than silently becoming generic attention.
5. `train/`, `inference/`, `architectures/`, `benchmarks/`, and `tests/` are project-level consumers of the public frontend and runtime APIs. Adopt Atma's separation of inference API/engine/scheduler/cache/model runner and training model/data/optimizer/loop, not Atma-specific model code inside URM.
6. No old-path compatibility modules, alias exports, dual registries, temporary name dispatch, or retained SDM-only plan/binder survive the cutover. Rewrite in-repository callers and documentation in the same change. Remove unsupported claims rather than keeping a fallback that bypasses the typed plan.

Proposed project tree (new `__init__.py` files in packages are implied):

```text
projects/urm/
  src/urm/
    frontend/                 # compile API, input schema/validation, JSON loader
    ir/                       # typed graph, K1/K2/K3 semantics, effects, state ABI
    compiler/
      common/ normalize/ rewrite/ partition/ select/ placement/
      schedule/ lower/ verify/ cost/ solve/
    runtime/                  # plan binding, operand validation, state sessions
    backends/
      interface.py            # pure capability and launcher contracts
      reference/numpy/        # independent float64/correctness equations
      reference/torch/        # differentiable reference equations
      triton/k1/ k2/ k3/      # native kernels and their narrow launchers
  recipes/
    kernels/*.json            # component/equation mappings and scope
    architectures/*.json     # complete graph, layer order, parameters, cache
    schema/                   # versioned recipe JSON schemas
  architectures/<name>/      # only model-specific components/loading/checkpoints
  train/                     # training application
  inference/                 # serving/generation application
  benchmarks/                # comparators, workloads, profiling, measurements
  tests/                     # fixtures, independent parity and integration tests
  results/                   # versioned evidence, not compiler inputs by default
```

## Required semantic and evidence corrections

- Compile a **graph of typed operations**, not an opaque `UnifiedMixerAccess` whose spec is later inspected by a separate executor. K1 covers routed/normalized reductions, K2 covers explicit state transitions and scans, and K3 covers selected state reads/writes. Route generation, parameter-axis transforms, projections, normalization, MLPs, and cache management are distinct graph nodes or external model components. A full model can invoke K1/K2/K3 multiple times; the three families are not three source files or three launches for a model.
- Remove architecture booleans, recipe-name branches, `EXTERNAL_OPAQUE` as a coverage shortcut, arbitrary `("...",)` tensor shapes, and candidate/anchor overrides that can select an incompatible equation. Semantic equivalence, input/output shape, dtype, state effects, training backward, decode state, and device support must be checked before an anchor is selectable.
- Make the serialized plan authoritative: each step names a typed operation, concrete backend capability, operands, layout, schedule, state transition, and backward/decode contract. Runtime executes those steps. A compiler result with no real schedule/cost for K1/K2/K3 is an explicit incomplete result, not a zero-cost choice.
- Extend analytical cost and schedule search to all three families. Account for useful versus wasted computation, route/index construction, gather/scatter traffic, SRAM/HBM movement, launch and synchronization costs, occupancy/register pressure, numerical/recompute cost, scan depth, state/cache traffic, backward, and graph critical path. Calibrate against measurements; retain uncertainty and rejected candidates. Probe exact compiled specializations only after legal analytical pruning.
- Separate evidence levels: semantic representation; independent reference parity; native kernel parity and performance; generic-model integration; **source-architecture** training/inference parity and performance. The current `master-table.md` and `benchmarks/master_table.py` put mixer fragments into one generic decoder, so their “model-level” label must become “generic decoder integration.” Those rows do not prove full Samba, PAttention, or other source models. Preserve measured numbers with corrected scope and provenance rather than rewriting them as stronger evidence.
- Samba needs a complete layer graph with its actual interleaving and state/cache branches. `samba_attention_core` may remain a K1 fragment JSON only, without full-Samba coverage credit. PAttention needs the parameter-token construction/reparameterization, parameter gradients, and model arrangement; its softmax contraction may remain a K1 fragment only. Apply the same boundary check to every other named recipe, especially hybrid, factorized, MoE, and stateful models.
- Reference backends must be independently implemented and reject unsupported semantics. Do not use the same optimized PyTorch path as both implementation and oracle. Keep float64 NumPy formulations, recurrence/slot VJPs, and source-specific comparator math where needed, but remove the separate `oracles` package.

## Executor instructions after the relocation cutover

The current primary compile path still calls `named_mixer_recipe` from the Python catalog in `frontend/recipes.py`, wraps the result in one `UnifiedMixerAccess` with placeholder shapes, and can dispatch execution from `CompiledMixerPlan.spec` and `backend` instead of its selected plan. A forced Polar anchor for plain MHA is accepted with zero useful FLOPs and no schedule. The K3 path still has a special `SparseMemoryPlan` and a binder that constructs `TritonSparseMemoryBackend` directly. Current Samba and PAttention architecture JSON files say `complete_model_graph` although each holds one fragment. These are acceptance failures, independent of the file moves.

### Remove source-specific contracts from the core

The cutover renamed files without removing their original responsibilities. `ir/program.py` still defines `SDMExecutionMode`, `SparseMemoryMixerSpec`, `SparseDeltaMemorySpec`, `SparseMemoryAccess`, `SparseDeltaMemoryAccess`, and `sparse_delta_memory_program`. `SparseMemoryMixerSpec.__post_init__` rejects shapes based on the frozen upstream SDM adapter, including divisibility by eight, read/write width limits, and training sequence length. Those are provider constraints, not mathematical IR. `frontend/recipes.py` contains a 74-name Python catalog before its JSON loader, and `compiler/pipeline.py` calls that catalog. The JSON kernel schema currently accepts one `UnifiedMixerSpec` with many architecture booleans and `additionalProperties: true`; the SDM JSON describes product-key routing only as a free-text external stage. A file being JSON does not make its graph executable or authoritative.

### Complete partitioning, scheduling, costing, and exact probes for all three families

`compiler/partition/` currently has only `k3.py`, and that file calls `sparse_delta_memory_program`, demands `NATIVE_SPARSE_MEMORY_ANCHOR_NAME`, and checks a hardcoded `native_route_then_partition_scan` schedule. It is an SDM-specific plan wrapper, not a graph partition pass. `compiler/schedule/probes/` has only `triton_k1.py`; that probe handles routed reduction and its row-scale epilogue, not the full K1 attention family. No K2 or K3 exact compile probe exists. The compiler accepts one injected probe callback, picks `schedulable_anchors[0]`, and `_search_schedule` returns `None` unless the graph contains `WeightedReduce`; multi-node K2/K3 schedules therefore cannot be proven by this path. `schedule/space.py` and much of `select/model.py` describe routed-epilogue knobs, while `cost/model.py` has routed reduction, row scale, and exchange formulas only. Its `combine()` takes the maximum of component critical paths without traversing dependent graph edges.

The adjacent packages have the same relocation gap. `normalize/` has only a docstring while builders remain in IR and `pipeline.py`; `rewrite/rules.py` registers only two row-scale rules; `lower/plan.py` currently stores a small backend choice rather than the executable step graph; `verify/plan.py` checks solver assignments, not the complete serialized plan; and `pipeline.py` still owns much of selection, scheduling, costing, lowering, and execution. Fill those stages with their stated contracts and move the implementation out of the monolith. A stage closes only when a graph passes through its code and the stage's output is independently checked.

### Build and prove the core in this order

1. **Choose one vertical slice and make it real:** load `recipes/kernels/mha.json` through the public frontend; normalize its equation into typed graph nodes with concrete shapes, dtypes, effects, and input/output edges; check complete anchor semantics; select and schedule a K1 implementation; lower to a serializable executable plan; bind and run that plan. Run an independently implemented reference on the same operands. A change to `spec.causal` in the loaded JSON must alter normalized IR and observable output on a discriminating input. Delete the Python named-recipe catalog and recipe-name compiler branches in the completed cutover. An explicit recipe root/configuration should make edited or externally supplied JSON testable without changing installed package files.
2. **Make plan binding the only execution route:** define a versioned plan step containing operation ID, capability ID, concrete tensor/state ABI, layout, launch schedule, and forward/backward/decode mode. `runtime/bind.py` validates the whole plan, resolves each step to a launcher, and executes steps and state effects in graph order. `CompiledMixerPlan.execute` must delegate to that bound plan; it must not inspect a retained `MixerSpec`, backend enum, or recipe name to choose another implementation. Incomplete or tampered plans fail before tensor execution. Delete `runtime/registry.py` and its old callers when the binder covers them; no compatibility export remains.
3. **Extend the same graph path across K1/K2/K3:** represent normalization/reduction, transitions/scans, route generation, ordered state update, and selected read as typed operations with explicit edges. Lower a K1→K2 graph and a route→K3 graph with at least two nodes each. Replace `compiler/partition/k3.py`'s special plan, `runtime/bind.py`'s direct K3 construction, and `backends/triton/k3/memory.py`'s score-to-state composition only when those graphs bind and run through the common path. Keep backend-local operand certificates that enforce launch preconditions; runtime checks the public plan/operand ABI, and a shared `runtime/operands.py` exists only if real cross-backend callers need it.
4. **Enforce semantic legality before tuning:** anchor matching must cover the equation, operands, shape, dtype, effects, state timing, backward, decode, and device modes. A user override is a request to evaluate one candidate, never permission to bypass these checks. MHA→Polar must fail compilation with a diagnostic naming the violated contract. For each family, enumerate legal schedules, prune with hardware resource bounds, rank with a shape-aware cost interval, probe exact specializations, and verify the selected result. Model K2 scan depth and state traffic, K3 route/index and collision work, backward traffic, launch overhead, and graph critical path as well as arithmetic. Treat unknown cost or schedule as incomplete. Prove sparse-work elimination, locality/fusion, scan reassociation, and route/state rewrites under typed preconditions; preserve a fallback candidate only when its semantics and cost are explicit. Put per-family capability, schedule, and cost logic in compiler stages as behavior appears; do not count empty subdirectories as an implemented pass.
5. **Close recipe and evidence semantics:** the architecture loader resolves every operation, edge, parameter transform, state/cache contract, and external component against a registered typed interface. It rejects unknown operations, dangling edges, invalid effect order, and unproved coverage assertions. Remove the current one-node Samba and PAttention files from `recipes/architectures/` until complete graphs exist; keep their K1 fragments in `recipes/kernels/` with fragment scope. A JSON `validated` flag is descriptive metadata and cannot grant source-model coverage. Rewrite `benchmarks/master_table.py` and its emitted table to call existing generic-decoder results “generic decoder integration”; retain measured numbers and provenance.
6. **Build the applications against that API:** keep the current SDM decoder as a benchmark fixture, construct a general decoder from a declarative model graph, create a training runner that accepts any model satisfying the public training interface, and implement a real prefill/decode inference engine. Follow the application and evidence worklist below. Existing benchmark step drivers and direct kernel decode tests remain evidence of their stated, narrower scopes. Source-faithful Samba/PAttention coverage waits for full graph, parameter mapping, gradients, decode continuity, comparator identity, and named performance measurements.

## Application and evidence worklist outside `src/urm/`

The 92-file disposition describes the old core files. It does not account for the work needed to turn the current project-level stubs and benchmark drivers into training, inference, or source-model applications. This is a separate required part of the refactor.

Begin the application slices as soon as the first JSON→plan→binder contract is stable; they do not need to wait for all named recipes or every native optimization. Their failures should feed back into the frontend, plan ABI, state contract, and compiler rather than creating an application-only dispatch path.

The training runner's input is a model built from a declarative graph, a batch/loss contract, an optimizer policy, and a state-boundary policy. The model owns its parameter transforms and bound mixer sessions; the runner owns data iteration, accumulation, backward, clipping, stepping, validation, and checkpointing. `train/` must contain no SDM/K1/K2/K3 or recipe-name dispatch. A graph that lacks a declared backward or state-training contract declines before the run starts. “All” means every graph that meets these contracts; representative K1, K2, K3, and mixed graphs are the regression set.

### Application delivery order

1. **Training slice:** define the application boundary around a graph-built model's forward/loss and bound state sessions, standard parameter/optimizer state, and an explicit sequence-boundary policy. Train tiny K1, K2, K3, and mixed-family decoders with the same runner on deterministic tokens; add a new JSON composition without changing `train/` to test generality. Run two optimizer steps for each, proving gradients, state policy, checkpoint/resume, and accounting. Then adapt the frozen FineWeb paired SDM benchmark without changing its existing evidence silently.
2. **Inference slice:** load the same model/checkpoint, prefill a prompt, decode several steps with its bound mixer state, and prove reference parity. Add batching, cache reuse, cancellation, and request-level measurements after the single-request contract passes. Repeat the state/caching qualification for every family advertised as inference-capable.
3. **Model scope:** build complete architecture graphs and source comparators one model at a time. Start with Samba's interleaved layers and PAttention's parameter-token transform. Keep fragment results and historical generic-decoder results separate until full training and inference parity is measured.
4. **Release evidence:** run CPU, PyTorch, GPU, and pinned-upstream suites in their provisioned environments; rerun affected benchmarks; update artifact schemas, generated tables, documentation, and packaging together. A core compiler gate, a training gate, a serving gate, and a source-model gate are separate verdicts.

## Completion gates for the single clean cutover

1. **Recipe authority:** the versioned JSON contains typed graph nodes and edges, not a serialized `UnifiedMixerSpec` with architecture flags. Changing an equation field changes normalized IR and observable execution; adding a valid JSON composition requires no Python catalog edit. Unknown operations, dangling graph edges, false full-model coverage flags, and unsupported external components are rejected before compilation. No Python named-recipe catalog or recipe-name switch supplies an equation.
2. **Semantic selection:** the normalized program has explicit typed nodes, shapes, effects, and state edges, with no SDM composite or architecture-named semantic switch. An incompatible forced anchor (for example Polar for plain MHA) is rejected before a plan is emitted. At least one multi-node K1→K2 graph and one route→K3 state graph compile without an opaque mixer node or a special SDM compiler entrypoint. Valid equations outside one provider's shape envelope reach reference execution and receive an explicit native capability decline.
3. **Plan authority:** K1, K2, and K3 plans survive serialization and binding; the runtime executes exactly the selected steps and schedule. Removing or changing a dispatch step, anchor, operand binding, or state contract either changes execution as prescribed or fails binding. The executor never reconstructs a route from the recipe name or backend enum.
4. **Numerical behavior:** independently implemented NumPy/PyTorch references agree with compiled forward results, gradients/VJPs where claimed, state continuity across chunks and decode steps, and declared numerical tolerances. Include dense and sparse K1, matrix and diagonal K2, and routed update/read K3; unsupported compositions fail explicitly. GPU-dependent claims require a provisioned GPU run.
5. **Decision quality:** partitioning covers K1, K2, and K3 regions with correct dataflow and state boundaries. Every schedulable region carries its own non-vacuous schedule and operation-appropriate cost estimate with uncertainty; dependent-region critical paths follow graph edges. Solver choices agree with exhaustive small cases, exact production-launcher probes for every claimed family/mode, and measured workload ranks. A zero-cost, unprobed optimization claim, or `None` schedule is reported as incomplete, never as a tuned plan.
6. **Training application:** one unchanged training runner accepts declarative K1, K2, K3, and mixed-family model graphs through the public frontend and bound plans, with correct gradient accumulation and per-model state policy, independent reference parity, deterministic checkpoint/resume, and an auditable optimizer/data/measurement boundary. A new supported composition requires a recipe/model change, not a `train/` code change. The preserved frozen SDM benchmark remains a separate comparison fixture and runs through the public application path. A direct K3 training kernel or benchmark-only `_one_step` does not satisfy this gate.
7. **Inference application:** a model checkpoint loads into an inference engine that runs prompt prefill and repeated decode through bound plans. Per-request states and caches remain isolated under variable-length batching, cancellation, and reuse; full-model logits match a reference. Request-level latency, throughput, and memory are measured separately from kernel-call timings.
8. **Model evidence:** representative source-model train and inference paths use only public URM APIs. Coverage tables distinguish fragments, generic-model integration, and faithful source models; Samba and PAttention need their full graph, parameter/state/cache mapping, gradients, decode parity, and source comparison before receiving model coverage credit.
9. **Repository boundary:** only after gates 1–8 pass, the inventory check accounts for all 92 old paths with no compatibility shims, static imports satisfy the core/application dependency direction, and a source scan finds no SDM/architecture-name policy in `src/urm/`. Package names or the number of moved files are not substitutes for these gates.

This plan intentionally does not prescribe a compatibility period. Land the refactor as one coordinated API, import, test, benchmark, and documentation cutover before treating `src/urm` as the stable core boundary.
